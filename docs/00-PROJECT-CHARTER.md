# Codex Monitor 项目章程

## 1. 项目结论

Codex Monitor 是一个轻量、常驻的 SwiftUI macOS 菜单栏应用。它把项目视为“部门”，把每个 Codex 任务视为“职员”，把用户视为“经理”。经理可以从一个工作台交办任务、巡视进度、处理举手授权并接收完成汇报。

首个可发布版本采用 **工作台托管 Codex App Server + 本机会话生命周期观察**。工作台创建或明确接管的任务提供权威状态与审批；独立 Codex Desktop、IDE 或 CLI 会话只读同步办理、完成、失败和中止，不承诺授权同步。产品不使用 Hook。

## 2. 问题定义

同时运行多个 Codex 项目和任务时，用户面临三个问题：

1. 状态分散：必须切换多个任务才能知道进度。
2. 注意力成本高：完成、失败、授权请求混在普通执行信息里。
3. 项目视角缺失：Codex 以任务为中心，用户需要以项目为单位管理工作负载。

产品应把“需要经理行动的任务”从普通运行状态中提取出来，同时保持界面紧凑，不复制完整聊天界面。

## 3. 用户与使用场景

### 3.1 核心用户

- 同时维护 2 个以上代码项目的独立开发者。
- 同时交办多个 Codex 任务的技术负责人。
- 需要在开发、测试、文档任务之间频繁切换的人。

### 3.2 核心场景

- 用户从工作台为一个项目交办任务，任务成为一张“职员卡”。
- 用户在写代码时，从菜单栏看到有 2 名职员举手。
- 用户打开工作单，核对操作范围并批准或拒绝一次授权。
- 职员完成后举手汇报，用户查看结果并标为已阅。
- 应用或电脑休眠后恢复，工作台重新校准状态，不展示过期申请。
- Codex Server 不可连接时，工作台明确显示“状态可能不是最新”。

## 4. 产品原则

1. **三秒可读**：三秒内识别所有待处理任务。
2. **行动优先**：授权、补充信息、失败和刚完成任务优先显示。
3. **控制与观察分离**：App Server 是托管状态和审批的唯一事实源；其他本机会话只显示带 `OBSERVED` 标记的生命周期观察值。
4. **人工授权**：任何权限决定都必须由经理明确点击，禁止自动批准。
5. **最终状态优先**：以最终 item/turn 事件纠正中间状态。
6. **离线诚实**：断线、事件遗漏或状态不确定时直接标明。
7. **少存数据**：不持久化完整对话、推理、命令输出和 diff。
8. **人格化但不幼稚**：使用经理、职员、柜台和举手隐喻，同时保留技术状态。

## 5. MVP 范围

### 5.1 必须包含

- SwiftUI 菜单栏入口和主窗口。
- Codex 安装、版本和 App Server 连接检测。
- 从工作台选择项目并交办新任务。
- 显式接管一个已保存任务并继续后续 turn。
- 项目自动分组：以规范化任务 `cwd` 为主键。
- 任务状态：运行中、等待中、举手申请、完成汇报、失败、中断、未知。
- 项目总览、紧凑职员卡、搜索和状态筛选。
- 授权、补充信息和完成事件的举手置顶与本地通知。
- 工作单内处理一次性命令、文件和权限授权；支持拒绝与取消。
- 任务详情：标题、项目、持续时间、最近活动、状态来源和更新时间。
- 断线重连、睡眠恢复、App Server 重启后的全量校准。
- 其他本机 Codex 会话的生命周期只读观察、来源标记和陈旧状态收敛。
- 隐私设置、连接诊断和最小审批审计。

### 5.2 延后到 v1.1

- `acceptForSession`、长期权限规则或自动批准策略。
- `turn/steer`、fork、批量中断和高级任务编排。
- 任务归档、删除和历史清理。
- 跨设备监控、远程连接、团队共享和云端遥测。
- 对完整聊天、推理或工具输出建立搜索索引。
- 与独立 Codex Desktop/IDE/CLI 进程共享权威 Server 状态或授权处理。

### 5.3 明确不做

- 替代 Codex 原生完整聊天界面。
- 把独立原生会话标为工作台实时任务。
- 安装或依赖 Codex Hook。
- 读取消息正文、工具输入、命令输出或 diff；生命周期观察只解析本机 rollout JSONL 的事件信封。
- 自动批准文件、命令、网络、MCP 或其他权限。
- 在未获同意时上传任务内容或项目路径。

## 6. 状态定义

| 产品状态 | 经理隐喻 | 触发依据 | 是否需要行动 |
|---|---|---|---:|
| `running` | 办理中 | 托管 thread 处于 active，或其他本机会话有 10 分钟内的新鲜 `task_started` 活动 | 否 |
| `waiting` | 等候安排 | idle 或尚未开始 turn | 否 |
| `needsApproval` | 举手申请 | Server 发起命令、文件或权限 approval request | 是 |
| `needsInput` | 请示经理 | Server 发起用户输入 request | 是 |
| `completedUnseen` | 完成举手 | turn completed 且经理未查看 | 是 |
| `completedSeen` | 已汇报 | 完成状态已被用户确认 | 否 |
| `failed` | 异常汇报 | turn failed、systemError，或近期观察到外部 `task_complete.error` | 是 |
| `interrupted` | 办理中止 | turn interrupted | 视情况 |
| `unknown` | 状态待核实 | 断线、版本不兼容或缺少最终事件 | 视情况 |
| `historyOnly` | 档案记录 | 非托管任务没有新鲜生命周期信号 | 否 |

“完成已阅”只改变本地工作台状态，不修改 Codex thread。

## 7. 成功指标

### 7.1 MVP 验收指标

- 冷启动后 3 秒内显示缓存与连接状态。
- App Server 可用时，活动状态变化到界面的延迟 P95 小于 1 秒。
- 授权请求出现到举手卡可见的延迟 P95 小于 1 秒。
- 用户点击审批到响应发出的延迟 P95 小于 200 ms。
- 审批 resolved 后，举手撤销延迟 P95 小于 1 秒。
- 睡眠恢复或 Server 重启后 5 秒内完成重新同步。
- 100 个任务、20 个项目下保持流畅；空闲 CPU 平均低于 1%，内存目标低于 120 MB。
- 不存在自动审批、跨任务审批或对过期 request 的响应。
- 无崩溃连续运行 8 小时。

### 7.2 体验指标

- 5 名目标用户中至少 4 名可在 3 秒内指出待处理数量和所属项目。
- 首次使用者无需说明即可区分授权举手、异常汇报和完成汇报。
- 用户可在两次点击内从菜单栏进入任一待处理工作单。
- 用户能够清楚理解“工作台托管”与“历史档案”的差异。

## 8. 项目约束与假设

- 初始部署目标为 macOS 14 及以上；开发机当前为 macOS 26.3。
- 使用 SwiftUI、Swift Concurrency、Observation 和 UserNotifications。
- 首期以个人本地分发为目标，不以 Mac App Store 上架为前提。
- 字体若打包 Manrope 和 IBM Plex Mono，发布前核对许可证并附带声明。
- 控制面仅使用官方 Codex App Server 接口和本机 stdio 传输；观察面只读访问 `~/.codex/sessions` 的生命周期事件信封。
- 当前安装无法启动 installer 管理的 daemon；这不阻塞应用托管 stdio Server。
- 工作台完全退出可能中断 active turn，因此退出前必须明确确认。
- 真实模型 E2E 测试可能产生用量，必须单独标识并人工启动。

## 9. 阶段闸门

| 闸门 | 决策问题 | 通过条件 | 未通过时处理 |
|---|---|---|---|
| G0 架构决策 | Server 托管边界是否明确且可实现？ | ADR 接受；跨实例限制有证据；不依赖 Hook | 缩减范围，不引入私有兼容层 |
| G1 产品设计 | 交办、举手、审批和完成语义是否清楚？ | 产品、设计、工程、QA 评审通过 | 修改 PRD 和原型 |
| G2 架构安全 | RPC 和审批边界是否可证明？ | 白名单、请求关联和迟到响应测试通过 | 阻止真实任务接入 |
| G3 MVP 完整性 | 托管任务核心闭环是否通过？ | P0/P1 用例全部通过 | 延迟发布 |
| G4 发布候选 | 性能、稳定性、隐私是否达标？ | 发布检查表全部通过 | 回到修复迭代 |

## 10. Definition of Done

MVP 只有在以下条件全部满足后才能称为完成：

- 目标设备上可安装、启动、退出和自动重连。
- 能由工作台创建真实 Codex 任务并按项目展示。
- 运行、授权、补充信息、完成、失败、中断和未知状态均有可复现测试。
- 一次性批准、拒绝、取消和过期 request 的端到端行为正确。
- 独立原生任务不会被错误标记为实时托管。
- RPC 白名单、审批 request 关联和退出保护由测试锁定。
- 应用不安装、不读取、不依赖 Hook。
- 无 P0/P1 缺陷；P2 缺陷均有接受理由。
- README、架构、测试、隐私和发布文档与实现一致。
- 用户可以清除应用自己的缓存、审计摘要和通知记录。
